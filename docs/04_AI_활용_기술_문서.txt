1. 요약
────────────────────────────────────────────────────────────────────────────────

  기획부터 코드·아트·밸런스까지 전 공정을 AI 도구로 수행했다. 다만 "AI에게
  맡겼다"가 아니라, 각 도구를 역할에 맞게 배치하고 그 산출물을 반드시
  기계적으로 검증하는 파이프라인을 세운 것이 핵심이다.

    기획   Claude 대화       →  요구사항 명세(PRD) 90개 항목으로 확정
    개발   Claude Code       →  PRD를 유일한 기준으로 구현 · 검증 · 리팩터링
    UI     Claude Design     →  화면 시안을 실제 렌더 가능한 목업으로 산출
    아트   Claude + GPT 이미지 →  테마 프롬프트를 Claude가 설계, GPT가 생성

  결과: 코드 약 7,000줄, 에셋 743개, 커밋 64개, 자동화 검증 3종
        (유닛 테스트 38개 / 봇 시뮬레이터 / 헤드리스 E2E 14체크)

3. 단계별 활용 내역
────────────────────────────────────────────────────────────────────────────────

■ 3-1. 기획 — Claude와의 대화로 PRD 확정

  "주식 차트로 타워디펜스를 만들고 싶다"는 한 줄에서 출발해, Claude와
  주고받으며 애매한 부분을 하나씩 결정 가능한 질문으로 바꿔 나갔다.

    · 만기제 예측 vs 자유 청산 → 선물식 자유 진입·청산으로 확정
    · 분봉 하루치 vs 일봉 장기 → 1봉=1거래일로 전환 (데이터 제약 해소 +
      코로나 폭락 같은 역사적 장세 확보)
    · 승패 판정 기준, 두 화폐 분리, 블라인드 공개 시점 등

  산출물: PRD_TICKER-FRONT_MVP.md (1,114줄 / FR 90개 항목)
  이 문서가 이후 모든 개발의 유일한 기준이 됐다. 기능마다 FR 번호가 붙어
  있어 코드 주석·커밋 메시지·테스트가 전부 같은 번호로 연결된다.

  [프롬프트 예시]
    "만기제로 하면 스캘핑이 최적해가 되지 않나? 자유 청산으로 바꾸되
     초단타가 이득이 없게 만들 수 있는 수식을 제안해줘. 근거도 같이."
    → σ30(30거래일 변동성)으로 정규화하는 손익 수식이 도출됨.
       짧게 보유하면 가격 변동폭이 작아 수익이 미미해지므로 스캘핑이
       자연 억제된다.

■ 3-2. 개발 — Claude Code로 PRD 기준 구현

  Claude Code에 PRD를 기준선으로 주고, 기능 단위로 구현·검증을 반복했다.
  단순 코드 생성이 아니라 다음 세 가지를 함께 수행하게 한 것이 특징이다.

    ① 구현        모노레포 4패키지 (shared / server / web / pipeline)
    ② 검증 코드    같은 커밋에서 테스트를 함께 작성
    ③ 문서 동기화  PRD의 해당 FR 항목을 실제 구현값으로 갱신

  [프롬프트 예시]
    "적을 잡으면 골드가 아니라 AUM이 오르게 해줘. 다만 그대로 주면 전투만
     해도 자본이 회복돼서 트레이딩을 안 하게 될 텐데, 상한을 어떻게 잡을지
     봇 시뮬레이터로 확인하고 정해줘."
    → 처치 보상을 초기 AUM의 20%로 상한 clamp. 서버가 클라이언트 보고를
       신뢰하지 않고 상한으로만 크레딧하는 구조까지 함께 설계됨.

■ 3-3. UI — Claude Design으로 화면 시안 산출

  Claude Design으로 타이틀·세계지도·전투·정산 화면의 시안을 뽑고, 그것을
  실제 게임 화면으로 옮겼다. 시안이 이미지가 아니라 실행 가능한 목업
  형태였기 때문에, 색·간격·폰트 같은 디자인 토큰을 그대로 추출해 코드의
  디자인 시스템으로 이식할 수 있었다.

    이식한 것
      · 팔레트 (상승 녹 #46A574 / 하락 적 #E8654F / 골드 #FFC53D)
      · 픽셀 문법 (라운드 없음, 3~4px 테두리, 오프셋 그림자 버튼)
      · 폰트 (Galmuri 픽셀 + IBM Plex Mono 숫자)
      · 화면 레이아웃 (타이틀 / 전략 상황실 톤의 지도 / 전투 3단 구성)

  전투 배경은 목업의 도시 실루엣을 파싱해 코드로 재생성하는 스크립트를
  만들어, 6개 도시 배경을 데이터로 뽑아냈다.

■ 3-4. 아트 — Claude로 프롬프트 설계 → GPT 이미지 생성

  가장 공을 들인 부분이다. 게임 테마(금융 용어를 의인화한 유닛, 픽셀·벡터
  혼합 톤)에 맞는 이미지를 얻기 위해, 프롬프트 자체를 Claude로 설계했다.

  [Claude에게 요청한 것 — 프롬프트 설계]
    "우리 게임 테마는 '금융 용어가 병사로 의인화된 방어전'이야. 유닛마다
     역할(탱커/근접/원거리)이 실루엣만 봐도 구분돼야 하고, 아군은 강철·황금·
     크림슨, 적군은 시안·마젠타 자체발광으로 진영을 나눠줘. 이 조건으로
     GPT 이미지 생성에 넣을 프롬프트를 유닛별로 써줘."

  [그 결과로 GPT 이미지 생성에 투입한 프롬프트 예시]
    "Side-profile pixel-art game sprite sheet, 4-frame walk cycle,
     'gas-mask gunner' — WWI trench aesthetic, steel #5A6376 and gold
     #C39C4C palette, crimson accent, facing right, transparent
     background, consistent ground line, no text"

  이렇게 생성한 원본을 그대로 쓰지 않고, 게임에 넣기 위한 규격화 작업을
  Claude Code로 수행했다.

    · 스프라이트 시트 규격 정리 (셀 크기·앵커·프레임 수 명세화)
    · 해상도 축소 (원본 19MB → 게임용 3.1MB, 렌더 크기 대비 과한 해상도 제거)
    · 발밑 앵커 정합 — 유닛마다 다른 키를 공통 px 공간으로 정규화해,
      배율 하나로 유닛 간 상대 크기가 유지되게 함
    · 타격 프레임 픽셀 측정 — 총구 화염이 몇 번째 프레임에 터지는지
      픽셀 단위로 분석해, 그 시점에 투사체가 생성되도록 맞춤

  최종 아트 물량
    캐릭터 18종 × (걷기 4F + 공격 5F) + 스킬 16종 + 투사체 7종
    포탑 3종 × (대기/조준 4F/발사 4F/투사체) + 도시 배경 3종
    합계 743개 파일


────────────────────────────────────────────────────────────────────────────────
4. AI 산출물을 신뢰하지 않기 위한 검증 체계
────────────────────────────────────────────────────────────────────────────────

  AI가 만든 코드와 수치는 "그럴듯하지만 틀린" 경우가 많다. 이를 걸러내기
  위해 세 겹의 자동 검증을 두고, 모든 변경마다 통과를 요구했다.

  ① 유닛 테스트 (38개)      전투 엔진·경제 수식의 규칙을 고정
  ② 봇 시뮬레이터           승률 p를 강제한 봇으로 지역별 클리어율을
                            수백 회 측정 → 밸런스를 감이 아닌 곡선으로 판단
  ③ 헤드리스 E2E (14체크)   실제 서버에 붙어 튜토리얼→클리어→보상→도감까지
                            전체 여정을 실시간으로 재현

  ■ 실제로 이 체계가 잡아낸 것들

    · 클리어율 0% 붕괴
      난이도 하향 요청이 여러 번 누적되면서 게임이 수학적으로 클리어
      불가능해진 상태를 발견. 계측 결과 마지막 웨이브의 총 체력이 아군
      화력의 4.4배였다. 감으로 조정하지 않고, 원인을 "적 개체 화력만
      웨이브에 비례해 커지는데 아군 유닛 체력은 고정"으로 특정한 뒤
      성장 기울기를 고쳐 정상 곡선(승률에 따라 7→47%)을 복구했다.

    · 넉백이 한 번도 작동하지 않던 버그
      코드상으로는 존재했지만, 판정 순서 때문에 기절과 교전 분기에 가려
      실제로는 단 한 번도 적용되지 않았다. 계측으로 "교전 중 이동량 0"을
      확인하고 순서를 교정했다.

    · 스킬 이펙트 오적용
      견습공의 평범한 망치 연타에 하늘에서 운석이 떨어지고 있었다.
      이펙트 종류를 공용으로 쓴 탓이었고, 전용 종류로 분리해 해결했다.

    · 투사체가 총구가 아닌 몸통에서 나가던 문제
      스프라이트의 총구 화염 위치를 픽셀 단위로 측정해 유닛별 발사 좌표를
      산출했다. 기본 공격과 스킬은 자세가 달라 총구 위치도 다르다는 것을
      측정으로 확인하고 각각 분리했다.


────────────────────────────────────────────────────────────────────────────────
5. AI 협업에서 얻은 교훈
────────────────────────────────────────────────────────────────────────────────

  ① 기준 문서가 없으면 AI는 방향을 잃는다
     PRD에 FR 번호를 붙여두니, 수십 번의 수정에도 "무엇을 왜 그렇게
     정했는지"가 유지됐다. 코드·테스트·커밋이 전부 같은 번호로 묶인다.

  ② "그럴듯함"과 "맞음"은 다르다
     AI가 제안한 수치는 언제나 그럴듯했지만, 실제로 측정하면 자주 틀렸다.
     밸런스는 반드시 시뮬레이터로 곡선을 그려 확인했다.

  ③ 이펙트와 판정을 일치시키는 건 사람이 지정해야 한다
     "곤봉을 내리찍을 때 데미지가 들어가야 자연스럽다" 같은 감각은
     AI가 먼저 챙기지 않는다. 스프라이트의 타격 프레임을 측정해
     판정 시점을 맞추는 작업은 명시적으로 지시해야 했다.

  ④ 생성 아트는 '규격화'가 절반이다
     이미지 생성 자체보다, 셀 크기·앵커·프레임 타이밍을 명세로 정리하고
     게임 좌표계에 정합시키는 작업이 훨씬 오래 걸렸다.

  ⑤ AI가 임의로 판단한 부분은 반드시 드러내야 한다
     요청하지 않은 수치를 AI가 "보정" 명목으로 바꾼 적이 있었고, 그것을
     명시적으로 보고하고 되돌렸다. 무엇이 지시이고 무엇이 AI 판단인지
     구분해 기록하는 것이 협업 품질을 좌우했다.
